## At the park on 2026-11-10: booking is off

The first real use showed that every Lightning Lane offer BG1 asks for is
answered with 403. Disney rejects the bot-protection tokens BG1 gets from the
upstream backend on offers and bookings, from any address and with any app
identity, while still accepting them for the party and needing none for the
tip board. Upstream removed booking for the same reason in November 2025
(`6c069e3`, `3eaf2a4` on `origin/main`); plans 001, 004 and 005 improve a
booking path Disney does not currently allow.

What changed that day:

- Server jobs watch the tip board and notify instead of booking
  (`366eb31`, `AUTO_BOOK_ACTION=notify`, `WATCH_POLL_INTERVAL_MS`). Verified
  against Disney: a watch job ended `available` with a real return time.
- Push notifications had never been sent: `web-push` 4 has no default
  export (`611e4f9`). Verified end to end: a Chrome subscribed on
  bg1.abdels.dev received and showed "Lightning Lane available now" with a
  link to `/dlr` when a live watch job ended `available`. Delivery to an
  iPhone Home Screen app is unverified.
- Proxies, imitating the current official app and a token captured from it
  were tried and removed (`2b57b02`, `fb1b9d3`). BG1 does not try to get
  past Disney's bot protection.
- The booking screen points to the Disney app when Disney refuses an offer,
  and the panel says "watch" rather than "book". Disney publishes no link
  into either app. On an iPhone, Open the Disneyland app follows the scheme
  the app registers for itself (`cs-com.disney.DLR://`, seen in Abdel's
  capture), which launches it at its home screen; on Android, Chrome opens
  the app by package. My Disney Experience on iPhone still goes to the App
  Store. Unverified on a phone (`3139636`).

## Findings considered and rejected

- Rate limits and job caps on the API: the owner decided there are none; the
  service is for his family.
- Replacing `node-forge` to shrink the Disneyland bundle (292 kB, loaded once
  on the first Disneyland booking): the encryption must stay byte-compatible
  with what Disney decrypts, and a mistake breaks booking.
- Sharing one Disney login between several searches for the same account: it
  only matters if a login nears expiry mid-day and Disney rotates refresh
  tokens, which is unverified. Revisit once the refresh has been seen working.
- Making the home host configurable for local development: useful, but it
  touches the server's CORS list and nobody develops against a local server
  today.
- A named vendor chunk and emptying `dist/` before builds: cosmetic; Railway
  builds from a clean checkout.
- A Content-Security-Policy for the app shell: Disney's login runs in an
  iframe and loads Disney's script, so a safe policy needs its own
  investigation.
- The cancel-versus-booking race when a device has no notifications: the
  booking is recorded and shows in Plans; rare.
- Time-zone handling on the booking path, request pacing, login encryption,
  job tokens, push endpoint checks, `pnpm audit`, and behaviour lost in the
  redesign: all reviewed and found clean.
- Renaming the "LL" tab to "Lightning Lane" and enlarging the virtual queue
  clock: design choices for the owner, not defects.

## Direction, not planned

- A list of every running search on the home screen. Searches are stored per
  ride today, so a guest must open a ride to see or stop its search.
- Server searches that modify an existing booking. The search loop already
  accepts a booking to modify; the job would need to carry it.
